oferece. O MCP é como

Não são concorrentes, e a pergunta "qual é melhor" não tem resposta. Por baixo, um servidor MCP quase sempre chama uma API. A diferença real está em quem lê o manual de instruções: você ou o modelo.

01 · Comece por aqui

A cozinha, o cardápio e o garçom

Antes de qualquer sigla: as quatro peças desse arranjo já existem em qualquer restaurante, e o papel de cada uma é exatamente o mesmo.

A cozinha (a API) sabe fazer os pratos, mas não fala com o cliente. O cardápio (o MCP) traduz o que a cozinha faz para uma linguagem que o cliente entende. O garçom (o aplicativo com o modelo) lê o cardápio, decide o que pedir e leva o pedido. Quem manda ainda é você.

Por dentro: os nomes técnicos de cada peça

Na especificação, o garçom se chama host (o aplicativo — Claude Desktop, um assistente interno, um editor de código), e dentro dele roda um cliente MCP, que é a parte que conversa com o servidor. O servidor MCP é o cardápio: um programa pequeno que anuncia o que sabe fazer e executa quando chamado. A API é o sistema de verdade, que já existia antes de tudo isso.

A conversa entre cliente e servidor é feita em JSON-RPC 2.0 — um formato de mensagem antigo e sem nenhuma novidade. A novidade do MCP não é o transporte; é o combinado sobre o que se manda por ele.

02 · Definições sem jargão

O que cada um é, em uma frase

API

Um contrato de acesso

O sistema publica: "estes são os endereços que aceito, estes os dados que preciso receber, este o formato da resposta". Quem cumpre esse contrato é um programa que alguém escreveu à mão, depois de ler a documentação.

É uma tomada na parede: serve energia, mas não sabe quem vai ligar nela, nem para quê, nem se agora é uma boa hora.

MCP · Model Context Protocol

Um padrão de encaixe

Um jeito único de apresentar ferramentas a um modelo na hora em que ele está trabalhando: o nome da ferramenta, uma descrição em português comum e quais informações ela pede. O modelo lê essa lista e decide o que usar.

É o USB-C: antes, cada aparelho tinha o seu carregador exclusivo; depois, um formato só passou a servir para todos.

A frase que resolve 80% da confusão

A API é a capacidade. O MCP é a embalagem que torna aquela capacidade utilizável por um modelo sem que ninguém precise escrever código novo para cada caso.

03 · O problema que o MCP resolve

Doze fios ou sete

Este é o argumento que decide orçamento, e é o único que realmente importa na hora de escolher. Troque o botão e veja a diferença.

12 ligações para manter de pé

3 aplicações × 4 sistemas = 12 ligações escritas à mão, uma por uma. Qualquer campo que mude em qualquer sistema quebra até 3 delas ao mesmo tempo — e ninguém descobre até alguém reclamar.

Por dentro: por que 7 e não 12

São 3 aplicações ligadas ao servidor MCP mais 4 sistemas ligados a ele: 3 + 4 = 7. É a troca de uma conta de multiplicação (N × M) por uma de soma (N + M). Com 5 aplicações e 10 sistemas, a diferença sai de 50 ligações para 15.

O ganho não é só o número. É onde a manutenção mora: quando o sistema muda, um único servidor é corrigido e todas as aplicações compatíveis passam a funcionar de novo, inclusive as que você não escreveu.

04 · Diferenças que mudam a decisão

Lado a lado

Nove eixos. Só os que mudam alguma coisa na prática.

Quem consome
APIUm programa escrito por uma pessoa, antes de tudo começar.
MCPO modelo, na hora, dentro de uma conversa em andamento.
Como se descobre o que dá para fazer
APIAlguém lê a documentação e programa. Isso acontece semanas antes do uso.
MCPO aplicativo pede a lista pronta — tools/list — e recebe nomes, descrições e o que cada ferramenta exige.
Padronização
APICada fornecedor com sua convenção, sua senha, seu jeito de paginar resultado.
MCPUma forma só. Trocar de modelo ou de aplicativo não obriga a reescrever a integração.
Unidade de trabalho
APIUm endereço técnico: POST /v1/query. Não diz para que serve.
MCPUma ferramenta com intenção escrita: "buscar precedente por tema".
Custo de crescer
APIUma integração para cada par aplicação × sistema.
MCPUm servidor atende a todos os aplicativos compatíveis, inclusive os futuros.
Memória da conversa
APINão guarda nada entre uma chamada e outra. Lembrar é problema de quem chamou.
MCPHá uma sessão aberta, em que cliente e servidor combinam o que cada um sabe fazer.
Controle humano
APIO programa decide sozinho. Não existe um momento natural para alguém aprovar.
MCPO aplicativo pode mostrar cada chamada e exigir a sua autorização antes de executar.
Por onde trafega
APIPela internet, normalmente em HTTP.
MCPstdio quando o servidor roda na sua própria máquina; HTTP quando é remoto.
Relação entre os dois
APIÉ a fonte real da capacidade. Sem ela, não há o que expor.
MCPÉ a embalagem que torna a capacidade utilizável pelo modelo.

05 · Anatomia

O que tem dentro de um servidor MCP

São três tipos de coisa, e só três. Confundir uma com a outra é a causa mais comum de servidor mal feito — o sintoma é sempre o mesmo: o modelo faz coisa que ninguém pediu.

Tools

Ações

O modelo faz alguma coisa: consulta, cria, calcula, envia. É onde está 90% do valor — e todo o risco.

Numa vara: "consultar andamento do processo", "gerar minuta de despacho de saneamento".

Resources

Leitura

Conteúdo que o modelo lê como contexto, sem alterar nada: um arquivo, um registro, um trecho de base.

Numa vara: o inteiro teor de uma peça, a tabela de assuntos, o manual interno de rotinas.

Prompts

Roteiros

Instruções prontas que o servidor oferece a você — atalhos de fluxo de trabalho, não automação que roda sozinha.

Numa vara: "triar esta petição inicial pelo roteiro da secretaria".

Regra de projeto

Se alguma coisa muda o mundo, é ferramenta e precisa de aprovação. Se apenas informa, é leitura. Expor uma escrita disfarçada de leitura é o defeito de segurança mais comum em servidor MCP caseiro.

06 · Passo a passo

O que acontece quando você pede algo

Seis passos, do "veja se há precedente sobre isso" até a resposta na tela. O passo 04 é o que interessa a quem responde por governança.

  1. Conexão aplicativo ↔ servidor

    O aplicativo abre a conversa com o servidor e os dois combinam o que cada um sabe fazer. Ninguém chamou nada ainda; é só o aperto de mão.

  2. O cardápio chega servidor → modelo

    O aplicativo recebe a lista de ferramentas com as descrições. Essas descrições entram na cabeça do modelo — texto mal escrito aqui vira chamada errada lá na frente.

  3. O modelo escolhe modelo

    Você pede "veja se há precedente sobre X". O modelo lê o cardápio, escolhe a ferramenta que parece servir e monta os dados que ela exige.

  4. Você autoriza ponto de governança

    O aplicativo mostra exatamente o que vai ser chamado e com quais dados. Em fluxo bem configurado, nada executa sem o seu clique. É aqui que se prende a coleira — e é exatamente esse passo que costuma ser desligado "para agilizar".

  5. Execução servidor MCP → API

    O servidor faz o trabalho sujo: entra com a senha, chama a API de verdade, trata erro, percorre as páginas de resultado e organiza a resposta.

  6. Retorno modelo → você

    O resultado volta e entra no contexto da conversa. O modelo interpreta e responde — ou conclui que precisa chamar outra ferramenta, e o ciclo recomeça no passo 03.

Consequência prática

A qualidade de um MCP depende menos do código e mais da redação das descrições e do recorte das ferramentas. Ferramenta genérica demais — "executar consulta" — empurra a complexidade para o modelo e produz erro silencioso, do tipo que ninguém percebe até virar problema.

07 · Onde as pessoas erram

Quatro confusões que custam projeto

✗"O MCP substitui a API."

Não. O servidor MCP consome a API. Se a API é ruim, lenta ou incompleta, o MCP herda tudo isso e ainda acrescenta uma camada por cima.

✗"Vou expor tudo como ferramenta."

Cardápio grande piora a escolha do modelo e ocupa espaço na conversa. Exponha poucas ferramentas de intenção clara, não o espelho da API.

✗"Se é padrão aberto, é seguro."

O padrão define a forma da conversa, não quem pode o quê. Servidor de terceiro executa código com as suas credenciais. Trate como fornecedor: procedência, permissão mínima, registro de chamadas.

✗"Para automatizar isso, preciso de MCP."

Se o caminho é sempre o mesmo e não exige julgamento — mover arquivo, disparar relatório às 7h —, um script chamando a API é mais barato, mais rápido e mais fácil de auditar.

08 · Regra de decisão

Qual usar no seu caso

Responda as quatro perguntas pensando em um caso concreto seu. O veredicto muda conforme você responde.

Você consegue escrever o passo a passo completo antes de ver os dados?

O fluxo precisa rodar sozinho, em horário fixo, sem ninguém olhando?

O próximo passo depende do que for encontrado no passo anterior?

A mesma capacidade vai servir a mais de um assistente ou equipe?

Responda as quatro perguntas

O veredicto aparece aqui, com o motivo. Nenhuma resposta é salva nem enviada para lugar nenhum — tudo acontece dentro do seu navegador.

O teste de uma linha

Se você consegue escrever o algoritmo antes de conhecer os dados, use API. Se a próxima chamada depende do resultado da anterior de um jeito que você não sabe descrever de antemão, o MCP paga o próprio custo.

09 · Glossário de bolso

As palavras que aparecem em toda reunião

API
A porta de serviço de um sistema: o conjunto de endereços por onde outro programa pede coisas a ele.
MCP
Combinado aberto sobre como apresentar ferramentas a um modelo de IA. Criado pela Anthropic e publicado no fim de 2024.
Host
O aplicativo com o qual você conversa e que hospeda o modelo. Nesta página, o garçom.
Cliente MCP
A parte de dentro do aplicativo que fala com o servidor. Você nunca a vê.
Servidor MCP
Programa pequeno que anuncia ferramentas e as executa quando chamado. Roda na sua máquina ou na rede.
Ferramenta (tool)
Uma ação que o modelo pode disparar, com nome, descrição e a lista do que ela exige.
Esquema
A ficha que diz quais dados a ferramenta espera e de que tipo. É o que evita chute do modelo.
Contexto
Tudo o que está "na mesa" da conversa naquele momento. É finito: encher de ferramenta inútil piora a resposta.
JSON
Formato de texto para trocar dados entre programas. Legível por gente, com alguma boa vontade.
JSON-RPC
Convenção antiga para pedir "execute isto" a outro programa usando JSON. O MCP a reaproveita.
stdio
Conversa entre dois programas na mesma máquina, sem passar pela rede. Mais seguro por construção.
Endpoint
Um endereço específico dentro de uma API, como /processos/123.

Sobre estas informações. Os conceitos desta página — as três primitivas, o JSON-RPC, os transportes stdio e HTTP, e a arquitetura host–cliente–servidor — refletem a especificação do MCP como a conheço até meados de 2026.

O protocolo evoluiu rápido, e detalhes de autenticação e de transporte já mudaram mais de uma vez. Confirme em modelcontextprotocol.io antes de decidir arquitetura ou de escrever norma interna. Em particular, não tenho certeza do estado atual das exigências de OAuth para servidores remotos.
